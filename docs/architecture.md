# Architecture

The LLM boundary is provider- and model-agnostic: product and Agent services call
the common provider contract, which is implemented by local and OpenAI-compatible
adapters. Qwen is only a documented local evaluation model; replacing it does not
change business logic, but does require rerunning model-dependent evaluation.

## Boundary

The desktop follows one directional dependency:

```text
PyQt UI
  ↓
Services (workflow/orchestration)
  ↓
Core and domain models
  ↓
SQLite/Parquet | LLM provider manager | optional weather service
```

UI pages render state and initiate services. They do not classify points, assemble LLM
prompts, or calculate COP. Services coordinate reusable domain functions. Core modules
do not import PyQt. Storage owns persistence.

## Vision boundary

Drawing Intelligence keeps the same directional boundary:

```text
PyQt Drawing Intelligence page
  ↓
DrawingService (project persistence and review workflow)
  ↓
BaseDrawingDetector
  ↓
YOLODrawingDetector (optional local Ultralytics adapter)
```

The model is local and optional. A detector output is project evidence with a
`predicted` status, not an engineering fact; human review is required before manual
equipment association. Agent drawing tools are read-only.

## LLM boundary

Product services use `LLMManager.get_provider()` and the `BaseLLMProvider` contract,
never a provider-specific SDK. `LocalLLMProvider` wraps optional Ollama use;
`OpenAICompatibleProvider` supports OpenAI, OpenAI-compatible service, open-source LLM API, LM Studio, vLLM, and
other compatible endpoints. `UnconfiguredProvider` is the normal fresh-install state
and returns a clear `LLM unavailable / not configured` result, leaving non-LLM flows
available. The legacy `LLMClient` facade remains only for compatibility with preserved
research adapters.

## Data flow

```text
CSV / Excel
  ↓
ImportService (sheet choice, time detection, quality metadata)
  ↓
Preprocessing
  ↓
SemanticService.analyze_dataframe()       ← the only formal entry point
  ↓
AnalysisResult
  ├─ semantic_results: list[SemanticResult]
  ├─ role_dict / ai_roles
  ├─ slot_details
  └─ unit_db
  ↓
ProjectStore (AI output + separate human review)
  ↓
Equipment model → AnalyticsService → structured Agent tools
```

The semantic pipeline runs once because every later consumer receives the same
`AnalysisResult`. Reclassification in the UI, COP code, reports, or Agent would create
irreproducible conflicts and is prohibited.

## Research and product modes

The default `SemanticService` path is the standalone product translation of the
current research baseline: strict eight-label semantics, V3 explicit non-target
engineering contradiction gating, and V4 structured equipment/loop/quantity
evidence. It has a deterministic fallback when no provider is configured and an
optional provider-neutral Direct LLM prior in enhanced mode.

`building_ai/research/` contains the older C1–C8 compatibility helper and frozen
prompt variants. It is available only through the explicit `legacy_c1c8` backend
for historical comparison; it is not the normal product pipeline. See
[research_to_product.md](research_to_product.md) for the selected boundary.

## Persistence

SQLite stores projects, semantic AI outputs, human reviews, import metadata, equipment
metadata, and agent session metadata. Parquet stores time series; CSV is an explicit
fallback when Parquet support is unavailable. Human review never mutates the stored AI
label. `effective_label` resolves the two views for downstream product use.

### Point identity and schema v2

`point_id = UUIDv5(project_id, normalized source_file, sheet, raw_name)` is the stable
database identity. `raw_name` remains a display value and a DataFrame column key only
within one imported dataset. `points`, `semantic_results`, and `human_reviews` join by
`point_id`. Agent point tools also require `point_id`; their mapping response includes
source and sheet provenance.

Database initialization reads `PRAGMA user_version`. A V1 database is migrated to v2 by
deriving point IDs from the provenance already stored in each semantic JSON payload,
copying reviews to the corresponding point, then setting schema version 2. Existing AI
predictions and human mappings remain separate.

### Unit-mode boundary

Product offline mode uses `core.unit_engine.infer_unit`. Research mode does not call that
engine. It extracts the raw C6 unit, type, and confidence from the same cached slot response
generated by the C1–C8 run. This avoids an undocumented hybrid research/product result.

## Safety

There are no BACnet/Modbus/OPC write paths. Agent tools return structured data and reject
unverified ABSTAIN points. The intended control progression remains recommendation,
shadow mode, physical validation, human approval, then possible future integration.
