# 图纸研究资产接入审计（第一阶段）

审计日期：2026-10-13。结论：**ADAPT，真实研究闭环仍为 PARTIAL**。现有模型可以通过 BuildingAI 的 Vision Adapter 执行真实预测，历史标注可以继续审查；尚不能把历史图纸与现有 BEMS 认定为同一建筑、同一设备，也不能宣称已自动生成改造设计。

本文件只公开汇总和软件验证方法。原始文件名、私人路径、图纸、运行数据、权重、截图及数据库保留在本地审计记录中，不随仓库分发。

## 真实链路与容易误解的地方

可恢复的链路是：图纸/PDF → 栅格化或已有裁剪图 → YOLO 五列归一化标注 → 三类训练 → best 检查点 → 像素框 → 人工审查。历史参数和训练日志支持“训练曾被执行”；本轮预测结果支持“选定检查点现可执行”。训练日志中的历史精度不是本轮重新测得的指标。

旧 PDF 脚本包含 300 dpi 栅格化代码，本轮未执行；另一个生成 `.pt` 的脚本保存的是图像和标签张量，不能与训练好的检测器权重混为一谈。名为冻结层的脚本主要是加载和类别查询，还存在把类别字典当列表使用的问题；仅凭文件名不能认定已经完成冻结层实验。选定运行保存的参数没有给出已验证的冻结设置。

旧 CSV/工作簿/坐标脚本的进一步分析见[历史 Revit 审计](legacy_revit_visualization_audit.md)。历史缩放公式、单位、原点和旋转仍不足以支撑工程坐标输出。本轮没有调用旧环境、修改原始标签或接入 Revit。

数据 YAML 中的相对路径及旧绝对路径不能直接带进产品。BuildingAI 由用户选择本地权重和图纸，通过现有 `DrawingModelRegistry / YOLODrawingDetector / DrawingService` 运行；没有复制或重新实现 YOLO。

## 图纸实际有什么

| 本轮查看的样本类型 | 目视与真实推理 | 可用性边界 |
|---|---|---|
| 日文空调系统平面局部图 | 清晰可见空调符号、设备引注、窗、轴号、房间及管线文字；返回 16 框，其中 7 个 aircon、6 个 window、3 个 baseline_mark | 适合本地演示和后续标注复核；文字、编号和管线尚未被系统自动理解 |
| 另一日文设备系统图 | 具有设备符号和管线标注；返回 8 个 aircon 候选框 | 与第一张风格不同；不是 8 个都已人工验证，遮挡/重复/漏检仍需评估 |
| 中文客房建筑平面图 | 返回 8 框；其中 aircon 落在床具附近，存在明显误检 | 不用这些错误候选证明空调定位成功；旧标签也有疑似非空调对象，保留原 GT 并另建问题清单 |
| 中文大型建筑首层平面图 | 人能读到“空调机房”等信息；模型返回 4 个 aircon 候选 | 有空调相关文字不等于模型已识别机房或设备身份；不是当前正向闭环样例 |

当前能自动得到：类别、置信度、原始图像尺寸、像素框、图像相对中心。人可利用清晰的原图编号、房间文字和图例进行核查，但本轮没有实现编号文字识别、房间分割、楼层恢复或连接拓扑推断。

可辅助的问题定位：回到原图查找已确认对象、核查对应设备、提示窗户等部位需要现场补充资料。不能直接得到真实安装坐标、型号、容量、墙窗材料、传热系数、窗面积、建筑层数或节能率。图上有标注尺寸也不代表当前算法已完成比例尺、裁剪和旋转标定。

## 平台落地与证据保存

图纸页、诊断页新增三语言的“既有建筑节能建议”入口。AI 助手可以通过只读 `get_retrofit_review` 查询同一份结构化结果，例如“当前项目的既有建筑节能改造建议”。无需新增大模型服务，不依赖模型自由生成工程结论。

建议分三层：

1. 运行优化：仅整理已有确定性诊断及其证据，沿用现有通俗解释和检查步骤。
2. 设备级改造评估：独立标为一般工程复核清单；先核查设备与控制资料，不能因低 COP 就断言需要更换。
3. 建筑级改造评估：独立标为一般工程复核清单；窗户框只提示核查位置，不能证明围护结构性能差。

本轮清单来自产品内的通用工程提示，不伪称本项目测量结果或知识库已经检索出的条文。原有知识库查询仍可用于补充带来源的参考资料。

新增人工关联分为“候选关联”“有依据的人工确认”“软件测试引用”。正式身份确认必须记录复核人和同一建筑、同一设备的对应依据。历史关联不删除，但缺少身份记录的旧关联显示为待核实。重新审查对象会撤销其旧身份确认；更换图纸内容或框尺寸校验失败时，关联不进入建议的身份依据。测试引用和未经确认的预测不构成真实关联。

导出包含：项目 ID/数据版本、BEMS 导入哈希、图纸与对象 ID、图纸哈希、权重哈希与库版本、类别/置信度/像素框、人工审查与关联状态、复核人/依据/时间、诊断 ID/测量证据、建议来源。未知的成本与节能量保留为空；`design_ready=false`。对象审查及关联事件保存在项目数据库，不写回原始研究资料。

## Windows 原生 GUI 验证

在独立测试数据库中，通过可见 PyQt 窗口的文件选择器、按钮和控件执行，使用历史文件的本地副本；不是离屏假预测：

- 实际导入一份日文 BEMS 工作簿：1440 行、58 个运行列；人工按原列含义确认两项设备温度信号。
- 打开设备、能源分析与诊断页。项目能源、功率和温度视图可用；目标设备缺少流量和设备功率，COP/负荷等完整计算被明确拒绝，未形成正式诊断发现。
- 实际导入上述两张日文系统图，运行选定 YOLO，分别得到 16 和 8 个候选框；各目视复核一个空调符号，通过 GUI 确认。
- 尝试选择 BEMS 设备并保存候选关系，进入设备详情、分析和三层建议，导出像素位置及建议依据。
- 因为没有同一建筑及设备对应证明，两条关系都保持待核实。未把空调末端符号认作 BEMS 热源主机，也未把这次软件联动测试计入正式研究。
- AI 助手实际调用新只读工具，显示证据不足和三层复核清单；没有生成缺乏依据的 COP、故障原因或项目改造结论。
- 同一可见建议对话框切换中文、英文、日文，诊断对象序列化结果不变。重启测试检查人工关联与导出记录一致。

**结论：软件入口、预测、复核、候选关联、分析导航和建议证据导出已连通；真实工程身份链和可支持具体优化建议的运行数据仍不完整。** 正向的“已有诊断 + 明确设备身份”链路由独立合成单元测试验证，不冒充真实建筑验证。

## 复验方法

只读资产审计：`python scripts/audit_yolo_dataset.py --dataset <本地数据集> --output <数据集外的私有报告.json>`。报告包含文件名，应留在忽略目录。

Windows GUI：`python scripts/qa_functional_desktop.py --manifest <私有清单.json> --workspace <全新测试目录>`，随后同参数追加 `--reopen`。清单用 `retrofit_review: true`、`bems`、`weights`、`drawings`、`candidate_equipment`、`questions` 指定本地文件和待核实设备。两个真实样本及其精确哈希保留在本地执行记录中，不提供无授权的公开下载。

单元测试：`python -m pytest tests/test_retrofit_review.py`。完整研究路线和下一里程碑见[博士研究路线](drawing_to_retrofit_research_roadmap.md)。

本轮回归结果：全量 pytest 217 项通过；单 Agent 66/66，多 Agent 66/66，Agentic Acceptance 26/26，既有科研测试 19/19。三语言各 734 个 key，覆盖率及占位符检查通过。最终界面措辞调整后又通过 11 项语言与建议回归。Windows 原生工作流、实际 `python app.py` 启动/正常退出、重启复验均通过，无未处理界面异常。以上软件测试不替代跨建筑识别精度、真实设备身份或节能效果实验。
